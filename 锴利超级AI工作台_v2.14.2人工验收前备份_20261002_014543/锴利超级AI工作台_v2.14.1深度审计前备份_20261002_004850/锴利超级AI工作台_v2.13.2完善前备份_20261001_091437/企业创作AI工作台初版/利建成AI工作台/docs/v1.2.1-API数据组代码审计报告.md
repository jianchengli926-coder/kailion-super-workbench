## 1. api.js（744 行）

### 1.1 文件概述
统一 OpenAI 兼容 API 封装：`chatCompletion`（SSE 流式/非流式）、`imageGeneration`、`videoGeneration`（同步+异步轮询）、`model3DGeneration`、`listModels`、`testConnection`。所有方法统一走 `AbortController` + 超时 timer + 外部 signal 三级中止，并在 `finally` 中埋点 `APILogger.log`。

### 1.2 问题清单

#### 【中等】M1 — 流式响应中的服务端错误被静默吞掉，误记为成功
- 位置：`api.js:169-198`（`consumeSSE`）
- 现象：流式分支（`api.js:123` `if (body.stream && resp.ok && resp.body)`）只在 HTTP 层判断 `resp.ok`。一旦握手成功（200）后服务端在 SSE 流里回传错误事件，如 `data: {"error":{"message":"invalid model"}}` 或 `data: {"error":{...}}`：
  ```js
  const delta = j.choices && j.choices[0] && j.choices[0].delta && j.choices[0].delta.content;
  if (delta) { ... }          // delta 为 undefined，整行被忽略
  ```
  `consumeSSE` 正常结束返回空串 `''`，`chatCompletion:124` 直接 `return _alOut`，`finally` 中 `_alErr=null` → **APILogger 记为 status:'success'**，engine.js:277 落到 `return full || '（模型返回为空）'`。
- 后果：401/429/模型名错误等本应失败的调用，在流式模式下表现为"成功但空输出"，费用统计与日志失真。
- 建议：在 `consumeSSE` 内对 `j.error`（或 `j.choices[0].finish_reason==='error'`）做检测，命中即 `throw new Error(...)`，让外层 catch 正确记录 failed。

#### 【中等】M2 — 测试连接会污染 API 日志（且多记一条 chat 调用）
- 位置：`api.js:701-729`（`testConnection`）内部调用 `chatCompletion(..., {stream:false})`，而 `chatCompletion` 的 `finally` 必然 `APILogger.log({type:'chat',...})`。
- 后果：用户每点一次"测试连接"，日志列表就多一条 type=chat 的 `'hi'` 记录，并计入今日调用数/费用。`api-logger.js:245` 虽预留了 `al.typeTest` 标签，但 api.js 从不产生 type='test'。
- 建议：给 `chatCompletion` 增加 `opts.silent`（或 `opts._isTest`），为真时跳过 `APILogger.log`。

#### 【轻微】L1 — 多模态 messages 的 content 为数组时 token 估算失真
- 位置：`api.js:101-103`
  ```js
  return sum + String((m && m.content) || '').length;
  ```
  若 `m.content` 是 OpenAI 多模态数组（`[{type:'text'},{type:'image_url'}]`），`String(arr)` 得到 `"[object Object]"`，字符数严重偏小。
- 建议：遇到数组时仅累加 `content.filter(c=>c.type==='text').map(c=>c.text).join('')`。

#### 【轻微】L2 — listModels 未校验 key，且 data.data 非数组时潜在异常
- 位置：`api.js:672` 仅判 `!provider.baseurl`，未判 key（与其它方法不一致）；`api.js:684`
  ```js
  const arr = (data && data.data) || (Array.isArray(data) ? data : []);
  const ids = arr.map(...)   // 若 data.data 是对象而非数组，此处抛错
  ```
  好在被 `catch` 吞掉返回 `[]`，不影响稳定性，但属隐性假设。

#### 【轻微】L3 — 全部错误信息硬编码中文，未走 i18n
- 位置：`api.js:86,136,143,145,215,269,276,278,374,419,451,455,460,462,549,600,630,634,639,641,718,724-725` 等约 20 处 `throw new Error('中文...')`。
- 这些 message 经 `testConnection` / engine catch 后直接 toast 给用户。切到英文界面时仍显示中文。
- 建议：错误文案改走 `I18N.t('api.err.xxx')`，与 api-logger 的 `L(key,zh)` 模式一致。

#### 【轻微】L4 — 文档与实际不符
- `api.js:9-11` 注释职责，及 providers-data 头注释"8 个供应商"实为 10 个（见 §3）。

### 1.3 重点验证：AbortController / 停止
- 外部 signal 接线正确：`api.js:106-111` 先判 `extSignal.aborted` 立即 abort，否则 `addEventListener('abort', …, {once:true})`。
- 超时 timer（`113/240/398/573`）与外部 abort 都走同一个 `controller`，并以 `abortedByTimeout` 标志区分"超时"与"用户停止"两种错误文案（`141-146`）。
- engine.js 侧：`engine.js:962` 每节点建 `execCtl` → `963` 加入 `activeControllers` → `964` 经 `opts.signal` 传入；`requestStop()`（`engine.js:36-40`）遍历 abort 并 clear；`engine.js:1153` 在 finally 中 `activeControllers.delete(execCtl)`。**停止链路完整、无控制器泄漏。**
- 轮询期间可中止：`sleep(ms, controller.signal)`（`api.js:486-500`）正确监听 abort 并 reject `AbortError`。

### 1.4 重点验证：多供应商统一接口 / 响应兼容
- `buildHeaders`/`normalizeBaseUrl`/`buildUrl` 统一去尾斜杠，路径拼接无重复斜杠。
- 图片兼容 `{data:[{url|b64_json}]}` 与中转站 `{images:[{url}]}`（`256-267`）；视频/3D 的 `extractVideoUrls`/`extract3DUrls` 兼容 `data/video/output/顶层` 多字段，空引用防护到位（`if (!data) return []`、`typeof === 'object'`）。
- JSON.parse 均有 try-catch：`readBody`（`69-72`）、SSE 单行解析（`186-194`）。
- **已知局限（文档已声明）**：Anthropic 原生 `x-api-key`/`anthropic-version` 未特殊处理，仅在 testConnection 失败时提示（`723-725`）。

## 2. api-logger.js（383 行）

### 2.1 文件概述
API 调用日志 + 费用估算：FIFO 保留 200 条，localStorage 持久化；内置模型定价表与图片/视频/3D 按次固定费用；`stats()` 聚合总/今日/本周；`render()` 渲染统计卡片 + 可筛选列表，事件委托绑定 `container.onclick`。

### 2.2 问题清单

#### 【轻微】L1 — 历史费用快照不随定价更新
- 位置：`api-logger.js:166` `cost: estimateCost(call)` 在写入时即固化。`setPricing`（`106-114`）改价后，旧日志仍按旧价，`stats()` 汇总的是历史快照。
- 这通常是合理设计（账单应定格），但若产品期望"按最新价重算"，则缺一个重算入口。建议在 README 注明口径。

#### 【轻微】L2 — `estimateCost` 模糊匹配依赖插入顺序
- 位置：`api-logger.js:131-138`，按 `Object.keys` 顺序首个包含即命中。定价表中 `'gpt-4o'` 先于 `'gpt-4o-mini'`；对一个未精确命中且同时包含两个 key 的模型串可能命中更宽的那个。当前定价表无实际冲突，属潜在隐患。

#### 【轻微】L3 — `type:'test'/'models'` 为死标签
- `api-logger.js:245-246` 定义了 test/models 标签，但 api.js 从不产生这两类记录（listModels 不写日志；testConnection 走 type=chat，见 §1 M2）。

#### 【轻微】L4 — `formatCost` 固定 4 位小数
- `api-logger.js:255` `'$' + usd.toFixed(4)`，累计总费用较大时仍显示如 `$12.3456`，阅读略繁琐。建议大额自动切 2 位。

### 2.3 验证通过项
- **空引用安全**：所有渲染字段均 `escapeHtml`（`233-237`），provider/model/error 无 XSS。
- **错误处理**：`loadLogs/saveLogs/loadPricing` 全部 try-catch，JSON.parse 失败回退空数组/默认值。
- **事件监听无泄漏**：`container.onclick=` 赋值式（非 addEventListener），每次 render 整体覆盖，不累积。
- **费用公式正确**：`(inTok/1e6)*p.input + (outTok/1e6)*p.output`（`143`），按次类型走 `TYPE_FLAT_COST`。
- **今日/本周统计**：`formatDateShort` 一律读本地时区分量，`todayStr` 与日志时间同口径；周一计算 `getDay()||7` 正确（周日=7）。
- **i18n**：21 个 `L('al.*')` key 全部在字典中存在（脚本校验 0 缺失），且均有中文兜底。

## 4. cache.js（194 行）

### 4.1 文件概述
节点结果缓存：djb2 哈希 + 参数排序做 key，LRU 淘汰 50 条，单条 4MB 上限，纯 localStorage。

### 4.2 问题清单

#### 【轻微】L1 — 每次读缓存都触发一次 localStorage 全量写
- 位置：`cache.js:105-118` `get()` 命中后 `entry.ts=now; entry.hits++; saveAll(data)`。即每次命中都 read-modify-write 整个缓存对象。高频节点会有不必要的 IO。
- 建议：命中时仅在内存更新，防抖（如 2-5s 批量 flush）或退出时再落盘。

#### 【轻微】L2 — 缓存无 TTL，永久陈旧
- 无过期策略，模型/供应商更新后旧结果永久命中。建议加 `ts` 对比或可选 TTL。

#### 【轻微】L3 — 嵌套对象 key 不参与排序
- `cache.js:36-48` 仅对顶层 key 排序，嵌套对象内部键序不同会产生不同哈希。当前节点参数多为扁平字段，影响有限。

### 4.3 验证通过项
- 写缓存前 `JSON.stringify` 测大小（`131-135`），超限跳过；`saveAll` 配额满时按 ts 升序删最旧 10 条重试（`71-82`）；`evictIfNeeded` 按访问时间 LRU。
- `paramsHash` 注释要求 providerId 参与哈希——engine.js 实际把 `__input` 与 `node.params`（含 providerId）一起传入（`engine.js:975-977`），跨供应商隔离成立。

## 8. 总结

本组代码整体工程质量**良好偏上**：统一的 AbortController+超时+外部信号三级中止、完善的空引用防护、try-catch 全覆盖、事件委托无泄漏、i18n 字典 1140 key 零缺失对称，均为亮点。

最值得优先修的 3 项：
1. **【M1】api.js 流式 SSE 内错误被吞** → 导致失败调用误记成功，建议在 `consumeSSE` 识别 `j.error` 并 throw。
2. **【M2】testConnection 污染日志** → 给 chatCompletion 加 silent 选项。
3. **【安全】全量备份明文含 API Key 且导入无确认** → 导入加 confirm、导出对 key 脱敏。
