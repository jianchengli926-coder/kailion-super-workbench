# 三工作台优点整合说明

> 记录锴利超级AI工作台从三个工作台各吸收了什么优点、如何整合、技术决策依据。

---

## 一、底座选择：利建成AI工作台

### 选择理由
经过对三个工作台的深度代码分析和功能对比，最终选择**利建成AI工作台**作为整合底座，原因如下：

| 维度 | 利建成AI | KaiLionCreator | KaiLionCrafts |
|------|----------|----------------|---------------|
| UI/UX精致度 | ⭐⭐⭐⭐⭐ 6套主题+自定义配色 | ⭐⭐⭐ 品牌金调单主题 | ⭐⭐ 单文件内嵌样式 |
| 功能完整度 | ⭐⭐⭐⭐⭐ 68节点13分类 | ⭐⭐⭐⭐ 74节点14分类 | ⭐⭐⭐ 基础节点 |
| 稳定性 | ⭐⭐⭐⭐⭐ 三轮审计修复144bug | ⭐⭐⭐⭐ ES Module架构 | ⭐⭐ 单文件 |
| 国际化 | ⭐⭐⭐⭐⭐ 1150条中英双语 | ⭐⭐ 中文为主 | ⭐⭐ 中文为主 |
| 模板生态 | ⭐⭐⭐⭐⭐ 20分类+25示例+版本历史 | ⭐⭐⭐ 工作流模板 | ⭐ 无 |
| 代码架构 | ⭐⭐⭐⭐ 全局变量IIFE | ⭐⭐⭐⭐⭐ ES Module三层 | ⭐ 单文件 |
| Office生成 | ⭐ 仅Markdown文本 | ⭐⭐⭐⭐⭐ 真实OOXML | ⭐ 无 |
| API协议 | ⭐⭐ OpenAI兼容仅1种 | ⭐⭐⭐⭐⭐ 4种协议 | ⭐⭐ OpenAI兼容 |
| 业务专属 | ⭐ 通用 | ⭐⭐⭐⭐⭐ 锴利专线6节点 | ⭐⭐ 基础 |

**结论**：利建成在UI/UX、功能完整度、稳定性、模板生态上全面领先，是最佳底座。KaiLionCreator在Office生成、API协议、业务节点上有独特优势，作为功能增量移植。KaiLionCrafts的专家库数据丰富，作为数据补充。

## 二、从KaiLionCreator吸收的优点

### 1. 真实Office文件生成（最大优点）
**源文件**：`js/core/ooxml.js`（931行）+ `js/core/zip.js`（205行）

**整合方式**：
- 将ES Module转为IIFE全局变量模式（`window.OOXML` / `window.ZipUtil`）
- ooxml.js内部对makeZip/bytesOf的调用改为通过全局`ZipUtil`调用
- 在engine.js中为Word/Excel/PPT/HTML节点添加真实文件生成逻辑：
  1. 先调用LLM生成Markdown格式内容
  2. 用OOXML.parseBlocks()解析为结构化块
  3. 用OOXML.renderDocument()生成对应格式的字节数组
  4. 创建Blob URL提供下载按钮
  5. 自动存入BlobStore

**效果**：Word节点产出可编辑的.docx，Excel产出带样式的.xlsx，PPT产出16:9可编辑.pptx。

### 2. 四套API协议
**源文件**：`js/core/protocols.js`（275行）

**整合方式**：
- 转为IIFE暴露`window.Protocols`
- providers-data.js供应商对象新增`protocol`字段（默认'openai'）
- 预设模板中Claude→anthropic, Gemini→gemini
- api.js的chatCompletion改为协议感知：根据供应商protocol字段分发到不同请求格式
- 智能纠偏：Base URL含anthropic.com自动用anthropic协议，含googleapis.com自动用gemini协议

**四套协议**：
- `openai` — /chat/completions（默认，兼容绝大多数中转站）
- `openai-responses` — /responses（OpenAI新版）
- `anthropic` — /v1/messages（x-api-key鉴权，max_tokens必填，system顶层参数）
- `gemini` — /models/{model}:generateContent（x-goog-api-key鉴权，model在URL路径）

### 3. 锴利专线6个专属节点
**源文件**：`js/data/nodes.js`（锴利专线分类）

**整合方式**：
- 在nodes-data.js的window.NODE_DATA末尾追加第14个分类"锴利专线"
- 节点ID用kl-前缀避免与现有68节点冲突
- 金色#C9A227分类色

**6个节点**：
1. `klProductShotNode` 产品图精修 — 去背景/统一布光/金属拉丝质感
2. `klSpecSheetNode` 规格参数表 — 中英双语规格表（钢材/HRC/刃长/MOQ）
3. `klInquiryReplyNode` 询盘邮件生成 — B2B买家类型识别+英文回复
4. `klCertPackNode` 出口合规包 — FDA/LFGB/REACH/Prop 65
5. `klSiteCopyNode` 独立站文案 — SEO+JSON-LD结构化数据
6. `klSupplierScoreNode` 供应商评分 — 加权评分+议价判断

### 4. 真实SKU数据和专家库
**源文件**：`js/data/library.js`

**整合方式**：
- 12位专家、10条提示词、6个SKU、5个数字人、6种风格、6个角色、8个场景、8个选题、6条知识库
- 全部合并到super-data.js的window.SUPER_DATA

### 5. BlobStore文件管理
**源文件**：`js/core/blobstore.js`（269行）

**整合方式**：
- 转为IIFE暴露`window.BlobStore`
- IndexedDB存储大文件（GB级配额），localStorage只存元数据
- 存Blob而非base64（省33%体积）
- objectURL缓存
- Office节点生成的文件自动存入BlobStore

### 6. ES Module三层架构思路
KaiLionCreator的core/data/views三层分层架构思路被记录，但考虑到利建成已有的全局变量IIFE架构更稳定且经过三轮审计，未做架构重构，仅做增量功能移植。

## 三、从KaiLionCrafts吸收的优点

### 1. 30位专家库
**源文件**：`KaiLionCrafts工作台.html`（单文件中提取）

**整合方式**：
- 从272KB单文件HTML中提取EXPERTS数组
- 与KaiLionCreator的12位专家合并，按name去重（"供应链专家"重名1个）
- 最终41位专家，存入super-data.js

### 2. 27条提示词库
**源文件**：同上

**整合方式**：
- 提取PROMPTS数组
- 与KaiLionCreator的10条合并，无重名
- 最终37条提示词，存入super-data.js

### 3. 单文件便携思路
KaiLionCrafts的单HTML文件便携思路被记录为可选功能。当前超级工作台采用多文件架构（利建成底座），因为多文件更易维护且功能更完整。启动脚本（.bat/.command/.vbs）提供了便捷启动方式。

### 4. 启动脚本
**源文件**：`启动工作台.bat` / `启动工作台.command` / `启动工作台.vbs`

**整合方式**：
- 复制三种启动脚本并修改为打开index.html
- .command已设置可执行权限
- 品牌名替换为锴利超级AI工作台

## 五、技术决策与注意事项

### 1. ES Module → IIFE转换
KaiLionCreator使用ES Module（import/export），但利建成使用全局变量IIFE模式。由于file://协议下ES Module有CORS限制，所有移植的模块均转为IIFE包装，通过window暴露全局变量。

### 2. 加载顺序
index.html中脚本加载顺序经过精心设计：
```
nodes-data.js → super-data.js → i18n.js → zip.js → ooxml.js → protocols.js
→ providers-data.js → api.js → blobstore.js → api-logger.js → cache.js
→ nodes.js → canvas.js → engine.js → ...其余模块
```
- zip.js必须在ooxml.js之前（ooxml依赖ZipUtil全局）
- protocols.js必须在providers-data.js和api.js之前（api依赖Protocols全局）
- blobstore.js在api.js之后、engine.js之前

### 3. localStorage key统一
全部使用`ljc_`前缀（利建成超级），避免与其他工作台数据冲突。

### 4. 向后兼容
- 旧供应商数据（无protocol字段）自动按openai协议运行
- 旧工作流文件可正常导入
- 所有利建成现有功能保持不变，仅做增量添加

### 5. 节点ID不冲突
锴利专线6个节点使用`kl`前缀（klProductShotNode等），与现有68节点的命名空间完全隔离。
